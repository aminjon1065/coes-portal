# 03. Архитектура

## 1. Стиль

**Модульный монолит, feature-first, с машинно-проверяемыми границами модулей.**

Одно приложение API, один фоновый обработчик, одно веб-приложение. Внутри API — модули по предметным областям. Модули общаются прямыми вызовами внутри процесса через объявленный публичный интерфейс.

Развязка «порты и адаптеры» применяется **ровно в двух местах**, где замена реалистична:

1. Хранилище двоичных объектов (`store`): интерфейс `BlobBackend`, реализация `FilesystemBlobBackend`.
2. Медиасервер (`meet`): интерфейс `MediaBackend`, реализация `LiveKitMediaBackend`.

**Больше нигде портов, адаптеров, слоёв «домен/приложение/инфраструктура» и репозиториев поверх репозиториев нет.** Церемония ради церемонии на автономном исполнителе превращается в тысячи строк переходников, в которых теряется смысл.

Из предметно-ориентированного проектирования взято ровно два приёма:

- **Единый язык.** Каждый термин имеет одно русское наименование, один идентификатор в коде и одно имя таблицы (`13-ГЛОССАРИЙ.md`). Синонимы запрещены.
- **Агрегат как граница транзакции.** Изменение одного агрегата — одна транзакция. Перечень агрегатов — `04-ДАННЫЕ.md` § Агрегаты.

### Последствия выбора, принятые осознанно

| Последствие | Почему принято |
|---|---|
| Один процесс API — одна точка отказа | Процесс не хранит состояния; число экземпляров увеличивается настройкой запуска. При потолке памяти 32 ГБ второй экземпляр возможен только при отключённой записи совещаний |
| Модули нельзя разнести по серверам без переделки | Сервер один. Разнесение не требуется и не планируется |
| Одна база на все модули | Целостность обеспечивается базой, а не согласованием в программе. Одна резервная копия восстанавливает всё |
| Прямые вызовы вместо шины сообщений | Отладка распределённых отказов невозможна: человека, читающего код, нет |

### Отвергнутые альтернативы

Подробно — `adr/01-modulnyj-monolit.md`. Кратко:

- **Микросервисы** — распределённые транзакции в документообороте с версионированием при отсутствии человека для отладки.
- **Слоистая архитектура** — границы предметных областей не видны в структуре; всё стекается в общую папку сервисов.
- **Чистая или гексагональная целиком** — объём переходников превышает объём полезного кода.
- **Событийная архитектура, CQRS** — нагрузка на чтение и запись сопоставима, аналитика работает на тех же данных.
- **Несколько репозиториев** — изменение контракта API затрагивает сервер и клиент одновременно.

### Условие пересмотра

Стиль пересматривается, если **одновременно**: число одновременных сессий устойчиво превышает 500 **и** один модуль потребляет более 60 % процессорного времени. Первым выносится медиа- и файловая часть, а не разрезание предметных модулей.

### Что содержит `public.ts`

Только: функции прикладной логики, типы их аргументов и результатов, константы разрешений модуля. Запрещено экспортировать: объекты запросов к базе, внутренние типы строк таблиц, экземпляры соединений.

### Механизм проверки

`packages/eslint-plugin-coes/module-boundaries` и `dependency-cruiser`:

- импорт `apps/api/src/modules/X/**` из `apps/api/src/modules/Y/**` при `номер(X) >= номер(Y)` — ошибка;
- импорт чего-либо, кроме `modules/Y/public`, из другого модуля — ошибка;
- импорт `apps/api` из `apps/web` и наоборот — ошибка;
- импорт `packages/db` откуда-либо, кроме `apps/api` и `apps/worker`, — ошибка.

Входит в `pnpm verify`.

## 5. Сквозные механизмы

### 5.1. Идентификаторы

- Первичный ключ каждой таблицы — `uuid` версии 7, формируется в приложении (`packages/core/id.ts`). Упорядочен по времени, что даёт локальность в индексе и не раскрывает количество записей.
- Пользователю UUID не показывается **никогда**. В интерфейсе объект опознаётся регистрационным номером или наименованием.
- Регистрационные номера — `04-ДАННЫЕ.md` § Нумерация.

### 5.2. Время

- В базе — `timestamptz`, всегда UTC.
- В API — строка ISO 8601 с суффиксом `Z`.
- В интерфейсе — пояс `APP_TIMEZONE` (по умолчанию `Asia/Dushanbe`).
- Единственный источник текущего времени в программе — `packages/core/clock.ts`. Прямой вызов `new Date()` вне этого файла запрещён правилом линтера: иначе тесты на сроки хранения невоспроизводимы.
- «Дежурные сутки» — настраиваемый интервал (`DUTY_DAY_START`, по умолчанию `08:00`), а не календарные сутки.

### 5.3. Ошибки

Единый вид ответа при ошибке:

```json
{ "error": { "code": "ACCESS_DENIED", "message": "текст на русском", "details": {}, "requestId": "01JC..." } }
```

| Код | HTTP | Когда |
|---|---|---|
| `VALIDATION_FAILED` | 400 | Данные не прошли проверку схемы. `details.fields` — перечень полей с текстом |
| `UNAUTHENTICATED` | 401 | Сессии нет или истекла |
| `ACCESS_DENIED` | 403 | Объект существует, прав на него нет |
| `NOT_FOUND` | 404 | Объекта не существует |
| `CONFLICT` | 409 | Нарушено правило целостности: занятый номер, повторное действие |
| `PRECONDITION_FAILED` | 412 | Устаревшая версия объекта при одновременном изменении |
| `LIMIT_REACHED` | 409 | Достигнут предел из реестра пределов. `details.limit` — ключ предела |
| `RATE_LIMITED` | 429 | Превышена частота обращений |
| `INTERNAL` | 500 | Прочее. Текст пользователю не раскрывает подробностей, `requestId` показывается |

Правила:

1. Сообщение всегда на русском, всегда говорит **что случилось и что делать**. «Ошибка сохранения» — недопустимо. «Номер 12/2026 уже присвоен другому документу. Обновите страницу.» — допустимо.
2. `ACCESS_DENIED` возвращается вместо пустого списка (`05-ДОСТУП.md` § Поведение при отказе). Компромисс: отказ подтверждает существование объекта. Принят осознанно, `adr/11`.
3. `requestId` пишется в журнал вывода и показывается пользователю на экране ошибки: это единственный способ связать жалобу с записью в журнале.
4. Стек вызовов пользователю не показывается никогда.

#### Отказы на границе модуля

Правила выше описывают границу HTTP. Между модулями действует следующее, и другого способа сообщить об отказе не существует.

1. **Модули не возвращают признак ошибки значением. Модули бросают типизированное исключение `AppError`** из `packages/core/errors.ts`. Тип `Result` в системе отсутствует.
2. `AppError` имеет поля: `code` (одно из значений таблицы выше), `message` (готовый русский текст для пользователя), `details`, `cause`. Конструкторы-помощники: `accessDenied()`, `notFound()`, `conflict()`, `limitReached()`, `validationFailed()`, `preconditionFailed()`.
3. **Единственное место преобразования `AppError` в ответ HTTP — общий обработчик ошибок, зарегистрированный в `bootstrap.ts`.** Ловить `AppError` в `routes.ts` и `service.ts` ради формирования ответа запрещено; ловить его ради восстановления (например, повторной попытки) разрешено при условии повторного возбуждения.
4. Исключение, не являющееся `AppError`, преобразуется в `INTERNAL`, записывается в журнал вывода целиком и пользователю показывается только `requestId`.
5. **Транзакция агрегата открывается в `service.ts`** — в той функции, которая соответствует одному действию пользователя. `routes.ts` транзакций не открывает; `queries.ts` транзакций не открывает и получает соединение параметром. Вложенных транзакций нет: вызов функции другого модуля внутри транзакции передаёт ей то же соединение явным параметром.
6. **Запись журнала действий выполняется той же функцией `service.ts` в той же транзакции**, последним действием перед возвратом. Функция, изменившая данные и не записавшая журнал, — дефект (`05-ДОСТУП.md` § 9.3).

### 5.4. Идемпотентность

Каждый метод, создающий объект, принимает заголовок `Idempotency-Key` (UUID, формируется клиентом). Ключ и хеш тела запроса сохраняются в `sys.idempotency` на 24 часа. Повторный запрос с тем же ключом и тем же телом возвращает ранее сохранённый ответ; с тем же ключом и другим телом — `CONFLICT`.

Без этого двойное нажатие кнопки в момент сетевой задержки порождает два события с двумя номерами.

### 5.5. Одновременное изменение

Каждая изменяемая сущность имеет колонку `version integer not null default 1`. Клиент передаёт `If-Match: <version>`. Несовпадение — `PRECONDITION_FAILED` и текст «Запись изменена другим пользователем. Обновите страницу, чтобы увидеть изменения.» Молчаливая перезапись запрещена.

### 5.6. Журнал действий

Полное описание — `05-ДОСТУП.md` § Журнал действий. Архитектурно:

- Таблица `audit.event` — только добавление. Роль приложения не имеет прав `UPDATE` и `DELETE` на неё; это выдано на уровне базы, а не проверяется программой.
- Каждая запись содержит хеш предыдущей записи. Вставка сериализуется через `pg_advisory_xact_lock`.
- Каждый изменяющий метод API порождает **ровно одну** запись журнала. Метод, не породивший записи, — дефект.
- Запись журнала пишется в **той же транзакции**, что и само изменение. Журнал не может разойтись с данными.
- Команда `pnpm audit:verify` проходит цепочку и сообщает первую нарушенную связь.

### 5.7. Уведомления

- Таблица `notify.notification` — что произошло; `notify.delivery` — кому доставлено; `notify.acknowledgement` — кто подтвердил получение.
- **Подтверждение получения существует с этапа 0**, даже если ни один сценарий Выпуска 1 его не требует. Причина: возврат к оповещению личного состава по тревоге не должен требовать переделки модели (`01-ПРОДУКТ.md` § Не строим).
- **Канал доставки один: в системе.** Электронной почты нет ни в каком виде — ни значения в перечислении каналов, ни настройки, ни кода отправки (`01-ПРОДУКТ.md` § 5): реализация за выключенным флагом запрещена принципом П-4, а проверить второе значение флага нечем, поскольку почтового сервера не существует (Д-05). СМС отсутствуют как канал и не предусмотрены схемой.
- Доставка в открытый браузер — через веб-сокет; при отсутствии соединения уведомление ждёт в списке.

### 5.8. Фоновые задания

- `pg-boss` поверх той же базы. Отдельного хранилища нет.
- Задания: формирование отчёта, конверсия в PDF и Word, импорт слоя, импорт исторических данных, обход сроков хранения, выгрузка записи совещания, обход недоставленных уведомлений.
- Каждое задание идемпотентно и может быть перезапущено.
- Пользователь видит состояние задания на экране, породившем его, и получает уведомление по завершении.
- Долгие задания (более 5 секунд ожидаемо) **никогда** не выполняются в обработчике HTTP-запроса.

### 5.9. Оповещение открытых сессий

- Веб-сокет `/api/v1/stream`, одно соединение на вкладку.
- Между процессами — `LISTEN/NOTIFY` PostgreSQL. Полезная нагрузка сообщения ограничена 8000 байтами, поэтому передаётся только вид события и идентификатор; данные клиент запрашивает обычным методом API.
- Подписка проверяется по правам: на канал события подписан только тот, кто имеет право видеть событие.

### 5.10. Хранилище двоичных объектов

- Файлы лежат в файловой системе на медленном томе, путь — по хешу содержимого: `<том>/blob/<первые 2 символа>/<следующие 2>/<полный хеш>`.
- Метаданные — в `store.blob`: хеш SHA-256, размер, тип содержимого, имя при загрузке, кто и когда загрузил.
- Одинаковое содержимое хранится один раз; ссылок может быть много.
- Выдача файла — только через API, встречным потоком; прямой доступ обратного прокси к каталогу хранилища запрещён.
- **Проверка прав при выдаче.** Одно и то же содержимое хранится один раз, поэтому ссылок на двоичный объект может быть много, и «проверить права по ссылающемуся объекту» без указания ссылки неисполнимо. Поэтому обращение обязано называть ссылку: `GET /blobs/{id}/content?ref=<видВладельца>:<идентификатор>`. Параметр `ref` обязателен; без него — `VALIDATION_FAILED`.
- **Как это не нарушает порядок модулей.** Модуль `store` (номер 9) не знает о модулях 11–19. Каждый модуль-владелец при сборке приложения регистрирует в `store` проверку для своего вида владельца: `registerBlobAccess('incident.attachment', fn)`. Регистрация выполняется в `bootstrap.ts` — единственном месте, которому разрешено импортировать все модули; сами модули друг друга по-прежнему не импортируют. Проверка получает сессию и идентификатор владельца и отвечает «доступно» или «нет».
- Порядок выдачи: найти ссылку `ref` в таблице владельца → убедиться, что она указывает на запрошенный двоичный объект → вызвать зарегистрированную проверку → выдать файл. Несовпадение ссылки и объекта — `NOT_FOUND`; отсутствие прав — `ACCESS_DENIED`. Вид владельца без зарегистрированной проверки — `INTERNAL` и запись в журнал вывода: это дефект сборки, а не отказ пользователю.
- **Крюк проверки** `BLOB_SCAN_COMMAND`: если настройка пуста (по умолчанию), файл принимается. Если задана — вызывается внешняя команда, ненулевой код возврата отклоняет загрузку. Это не отключённая функциональность, а точка подключения службы, которой у организации сейчас нет (`01-ПРОДУКТ.md` § Не строим).
- Удаление объекта из хранилища — только когда на него не осталось ссылок и истёк срок отложенного удаления `BLOB_GRACE_DAYS` (по умолчанию 30).

### 5.11. Настройки и пределы

- Настройки читаются в порядке: переменная окружения → строка в `sys.setting` → значение по умолчанию в `packages/core/limits.ts`.
- **Единственное исключение из этого порядка:** `BASE_URL`, `EXTRA_HOSTNAMES` и `REDIRECT_TO_BASE` хранятся **только** в `sys.setting` и переменными окружения не переопределяются. Причина: их меняют из интерфейса, и переменная окружения молча отменяла бы правку. `./deploy/install.sh --base-url` записывает значение **в `sys.setting`**, а не в окружение.
- Настройки, помеченные как изменяемые из интерфейса, редактируются на экране «Настройки системы» администратором системы и вступают в силу без перезапуска.
- **Числовая константа, ограничивающая работу пользователя, в коде запрещена.** Любое ограничение объявляется в реестре пределов, имеет ключ, значение по умолчанию, точку применения и текст отказа.
- Механизм проверки: `pnpm check:limits` — сборка падает, если ключ реестра не используется ни в одной точке применения либо не имеет текста отказа.

### 5.12. Поиск и полнотекстовый указатель

- Поиск — средствами PostgreSQL. Отдельной поисковой службы нет.
- Собственный словарь замен для таджикских букв (`04-ДАННЫЕ.md` § Поиск и сортировка) кладётся в образ базы.
- Условие пересмотра: p95 поиска превышает 500 мс при более чем 2 000 000 объектов.

### 5.13. Журналирование работы

- Структурированные записи в поток вывода (`pino`), формат JSON, поле `requestId` в каждой.
- Хранение — средствами Docker с ротацией: 10 файлов по 50 МБ.
- Систем сбора метрик нет. Состояние системы видно на экране «Состояние сервера»: свободное место на обоих томах, размер базы, число сессий, длина очереди заданий, время последней резервной копии, результат последней проверки целостности журнала.

### 5.14. Адрес системы, домен и переезд

Система разрабатывается и принимается **локально** (§ 11), а на сервере организации будет работать по имени, которое со временем сменится: сначала поддомен подрядчика `cmc.techdev.tj`, затем домен Комитета (Д-23). Раздел перечисляет **все** места, где имя может застрять, сводит их к одной настройке и задаёт механизм применения изменения.

**Единственный источник абсолютного адреса — настройка `BASE_URL`.** Значение вида `http://localhost:8080` (локально) или `https://cmc.techdev.tj` (на сервере), без завершающей косой черты.

#### Три настройки имени

| Ключ | Значение | Где хранится |
|---|---|---|
| `BASE_URL` | Основное имя. Из него собираются все абсолютные ссылки | **только `sys.setting`** |
| `EXTRA_HOSTNAMES` | Дополнительные имена через запятую. На них тоже выпускается сертификат, и они тоже считаются разрешёнными источниками. Используется в период, когда работают оба имени | **только `sys.setting`** |
| `REDIRECT_TO_BASE` | При значении «да» обращения по дополнительным именам перенаправляются на `BASE_URL` | **только `sys.setting`** |

#### Механизм применения изменения — обязательный

Без него период «оба имени работают одновременно» неисполним, а процедура переезда — единственная защита от отказа домена подрядчика — нерабочая.

1. **Разрешённые источники вычисляются на каждый запрос,** а не собираются при запуске. Множество разрешённых источников = `{BASE_URL} ∪ EXTRA_HOSTNAMES`, читается из `sys.setting`. Это касается: проверки заголовка `Origin` для защиты от подделки запросов, заголовков совместного доступа между источниками, директив `connect-src` и `frame-ancestors` политики безопасности содержимого. **Выводить их из одного `BASE_URL` запрещено:** тогда вход по второму имени отклонялся бы проверкой источника.
2. **Конфигурация обратного прокси перегенерируется при изменении настройки.** При сохранении `BASE_URL`, `EXTRA_HOSTNAMES` или `REDIRECT_TO_BASE` модуль `sys` перезаписывает файл `Caddyfile` из шаблона `deploy/caddy/Caddyfile.tmpl` и вызывает горячую перезагрузку прокси через его локальный управляющий адрес (`POST http://caddy:2019/load`, доступный только внутри сети контейнеров). Перезапуск контейнеров не требуется и не выполняется.
3. **Результат перезагрузки проверяется.** Если прокси вернул ошибку, настройка **не сохраняется**, а пользователю показывается текст ошибки. Молчаливое расхождение между настройкой и работающей конфигурацией недопустимо.
4. **Выпуск сертификата на новое имя.** После перезагрузки прокси получает сертификат на добавленное имя самостоятельно. Ожидаемое время — до 2 минут при подтверждении через записи DNS. Состояние видно на экране «Состояние сервера»; пока сертификат не получен, имя помечено как «сертификат ожидается».
5. **Локально шаги 2–4 не выполняются:** при `BASE_URL`, указывающем на `localhost`, обратного прокси и сертификатов нет вовсе (§ 11).

#### Где имя могло бы застрять

| Место | Правило |
|---|---|
| Ссылки в уведомлениях | В `notify.notification` хранится **относительный путь** (`entity_path`, например `/incidents/0193...`). Абсолютный адрес собирается в момент показа |
| Ссылки в задачах, документах и сообщениях, порождаемых системой | Только относительные пути |
| Записи журнала действий | Относительный путь запроса, без схемы и имени узла |
| Отчёты и печатные формы | Подстановка `${адресСистемы}` подставляет `BASE_URL` в момент формирования. Записанный в шаблон адрес запрещён (`04-ДАННЫЕ.md` § 11.3) |
| Адрес веб-сокета | Клиент выводит его из адреса текущей страницы (`window.location`) |
| Адрес сервера видеосвязи | Выводится из `BASE_URL`. **Отдельного имени у видеосвязи нет**: сигнальный канал проходит через тот же прокси по пути `/rtc`, ретрансляция использует то же имя, сертификат общий |
| Область действия cookie | Атрибут `Domain` **не задаётся**: cookie привязана к узлу и следует за именем сама. Следствие — при смене имени все сессии прекращаются (`05-ДОСТУП.md` § 10.3) |
| Разрешённые источники, политика безопасности, проверка `Origin` | Пункт 1 механизма выше |
| Конфигурация обратного прокси | Пункт 2 механизма выше |
| Переходы после входа, адреса перенаправлений | Только относительные пути |
| Пользовательский текст, куда сотрудник вставил ссылку вручную | Запретить нельзя. При переезде выполняется `pnpm urls:rebase --from <старое> --to <новое>` |

**Проверка.** `pnpm check:urls` обходит все текстовые и `jsonb`-столбцы базы и падает на значении, начинающемся с `http://` или `https://`, вне перечня разрешённых столбцов. Перечень разрешённых: `sys.setting.value` (ключи `BASE_URL`, `MAP_STYLE_URL`), `geo.map_layer.style`, `geo.map_feature.properties`, а также столбцы свободного текста, вводимого сотрудниками. Новый столбец попадает под проверку **автоматически**: перечень задаёт исключения, а не охват.

Процедура переезда — `12-ЭКСПЛУАТАЦИЯ.md` § 4. Проверяется приёмочным сценарием **ПС-0-13 на этапе 0, локально, на двух локальных именах**; повторяется на каждом этапе, где появляется новый вид ссылки (`10-ЭТАПЫ.md` § 1, п. 8).

## 6. Реестр пределов

Каждый предел — настройка. При достижении система **отказывает понятным сообщением и не деградирует молча**.

**Наборов значений по умолчанию два: локальный и продуктовый.** Локальная среда (§ 11.1) работает на машине с 16 ГБ памяти, продуктовая — на сервере с 32 ГБ; одно значение на обе среды означало бы, что исполнитель возьмёт продуктовое и локальная среда упадёт. Набор выбирается по значению `DEPLOY_PROFILE` (`local` или `server`), задаваемому файлом сборки, а не пользователем.

**Правило проверки пределов.** Локально проверяется **поведение** предела — что при достижении выдаётся понятный отказ. Продуктовое **число** проверяется на этапе В. Приёмочный сценарий формулируется через поведение, а не через число, поэтому проходит в обеих средах.

| Ключ | Локально | На сервере | Где применяется | Поведение при достижении |
|---|---|---|---|---|
| `LIMIT_MEETING_CONCURRENT` | 2 | 2 | `meet` | Отказ: «Идут два совещания. Начать третье нельзя. Дождитесь окончания одного из них.» |
| `LIMIT_MEETING_PARTICIPANTS` | **6** | 20 | `meet` | Отказ: «В совещании уже N участников — это предел.» |
| `LIMIT_MEETING_VIDEO_SUBSCRIPTIONS` | **3** | 9 | `web` | Не отказ: участник получает видео говорящих и закреплённых, остальные — только звук с портретом. Показывается пояснение |
| `LIMIT_RECORDING_CONCURRENT` | 1 | 1 | `meet` | Отказ: «Идёт запись другого совещания. Одновременно ведётся одна запись.» |
| `LIMIT_CONVERSION_CONCURRENT` | 1 | 1 | `worker` | Не отказ: очередь. Пользователю показывается позиция в очереди |
| `LIMIT_REPORT_ROWS` | **50000** | 200000 | `analytics` | Отказ: «Отчёт содержит более N строк. Сузьте период или добавьте фильтр.» |
| `LIMIT_EXPORT_PDF_PAGES` | 500 | 500 | `template` | Отказ: «Документ длиннее 500 страниц. Выгрузите в Excel.» |
| `LIMIT_UPLOAD_SIZE_MB` | **128** | 512 | `store` | Отказ: «Файл больше N МБ.» |
| `LIMIT_CHAT_ATTACH_MB` | **32** | 100 | `chat` | Отказ: «Файл в переписке — не больше N МБ.» |
| `LIMIT_DISK_FREE_GB` | **20** | 200 | `store`, `meet` | Отказ на загрузку и на начало записи: «На диске осталось N ГБ из необходимых M. Загрузка файлов и запись совещаний остановлены. Обратитесь к администратору.» |
| `LIMIT_MAP_FEATURES` | 5000 | 5000 | `geo` | Не отказ: показываются первые 5000 по релевантности и предупреждение «Показаны первые 5000 объектов. Уточните фильтр.» |
| `LIMIT_IMPORT_ROWS` | 200000 | 200000 | `worker` | Отказ до начала импорта с указанием числа строк в файле |
| `LIMIT_SESSION_PER_ACCOUNT` | 5 | 5 | `iam` | Не отказ: самая старая сессия закрывается, пользователь уведомляется |
| `LIMIT_LOGIN_ATTEMPTS` | 10 за 15 минут | 10 за 15 минут | `iam` | Отказ: «Слишком много попыток входа. Повторите через N минут или обратитесь к администратору.» |
| `LIMIT_LIST_PAGE_SIZE` | 200 | 200 | все реестры | Отказ на значение больше предела |
| `LIMIT_ATTACHMENTS_PER_CARD` | 50 | 50 | `incident`, `doc` | Отказ: «К карточке нельзя приложить больше 50 файлов.» |
| `LIMIT_LAYER_FEATURES` | 100000 | 100000 | `geo` | Отказ при импорте слоя |
| `LIMIT_JOB_RUNTIME_MIN` | 30 | 30 | `worker` | Задание прерывается, пользователь получает уведомление с причиной |

**Тексты отказов не содержат зашитых чисел** — число подставляется из действующего значения предела. Иначе локальный отказ сообщал бы продуктовое число.

| Том | Объём | Что хранит |

### Сеть

- Внутри организации при работе видеосвязи: **не менее 200 Мбит/с** в обе стороны на сервере.
- Удалённый участник совещания: не менее 4 Мбит/с на приём, 2 Мбит/с на передачу (Д-08).
- Расчёт при пределе 9 видеопотоков: приём участника ≈ 2,7 Мбит/с, передача ≈ 1,2 Мбит/с; два совещания по 20 участников ≈ 108 Мбит/с исходящих и 48 Мбит/с входящих на сервере.

Продуктовое распределение в 16 ГБ не помещается примерно вдвое, поэтому у локальной среды **собственный профиль**. Значения выбираются по `DEPLOY_PROFILE = local`.

### Сколько участников совещания помещается локально

Арифметика, из которой получено число:

- браузеру остаётся ~2,5 ГБ;
- собственные процессы браузера — ~0,5 ГБ;
- окно участника с включённой камерой (кодирование исходящего потока плюс декодирование входящих) — ~0,3 ГБ;
- `(2500 − 500) / 300 ≈ 6,6` → **6 участников**.

По процессору: Egress ~4 ядра, LiveKit ~1, шесть окон с кодированием ~3, база с API и обработчиком ~1 — итого ~9 из 10. Запас мал, но десятиминутного прогона хватает.

Отсюда локальные значения `LIMIT_MEETING_PARTICIPANTS = 6` и `LIMIT_MEETING_VIDEO_SUBSCRIPTIONS = 3` (§ 6). Второе выбрано не произвольно: при шести участниках каждому доступно пять чужих потоков, и предел в 3 **действительно срабатывает** — то есть механизм ограничения проверяется локально, а конкретное число 9 подтверждается на сервере.

Настоящая камера на машине одна, поэтому одно окно запускается с ней (это проверяет выдачу доступа браузером), остальные — с подменным источником видео браузера.

**Явное отступление.** Норматив Н-20 «совещание 20 участников без разрывов» локально **не проверяется и не может быть проверен**. Локально проверяются: работоспособность совещания, запись, все отказы по пределам и срабатывание ограничения на число принимаемых потоков. Число 20 подтверждается только на этапе В сценарием ПС-В-04. Последствие принято осознанно: если на сервере совещание на 20 участников не выдержит, это обнаружится на этапе В, а не раньше.

## 8. Нормативы производительности

**Эталонный набор данных** формируется командой `pnpm seed:bench`: 500 000 событий за 6 лет, 300 учётных записей, 1 200 подразделений, 60 000 пострадавших, 2 000 000 записей журнала действий, 40 слоёв по 5 000 объектов.

**Эталонное рабочее место** для клиентских нормативов: 4 ядра x86-64, 8 ГБ памяти, Chrome 120 и выше, разрешение 1920×1080.

**Где проверяются.** **Нормативы производительности проверяются на этапе В, на целевом оборудовании.** Локально их подтвердить нельзя и пытаться не нужно: у машины исполнителя вдвое меньше памяти, у PostgreSQL там 2 ГБ вместо 10, а нормативы Н-16 и Н-17 (150 и 300 одновременных сессий) на ноутбуке не имеют смысла вовсе.

Локально каждый норматив всё равно **измеряется и записывается в отчёт как справочное число** вместе с характеристиками машины — но порогом для приёмки этапа не является, и сценарий не считается непройденным из-за превышения.

**Единственное исключение — сторожевой порог.** Локальный замер, превышающий норматив **более чем в 10 раз**, считается дефектом этапа. Десятикратное отставание не объясняется разницей в железе: это отсутствующий индекс, запрос в цикле или выборка всей таблицы. Порог грубый намеренно — он ловит ошибку устройства, а не разницу оборудования.

**Метод замера.** `pnpm bench` — 200 повторов каждого обращения к работающему API, отчёт по медиане и 95-му перцентилю. Клиентские нормативы — Playwright с замером до события `networkidle` и до появления первой строки данных.

## 9. Надёжность

Сервер один, резерва нет. **Высокая доступность не обещается и не проектируется.** Обещается следующее:

- Потеря данных при аппаратном отказе — не более 15 минут. Достигается непрерывной архивацией журнала транзакций PostgreSQL на медленный том, отдельный от SSD с базой.
- Ночная копия на внешний носитель (Д-17).
- Восстановление после аппаратного отказа занимает **часы**, а не минуты. Это записано прямо и не приукрашивается.

**Проверенная процедура восстановления важнее любых цифр.** Поэтому:

1. Процедура описана в `12-ЭКСПЛУАТАЦИЯ.md` как одна команда `./deploy/backup/restore.sh <метка времени>`.
2. Её прохождение входит в приёмку этапа 0 (ПС-0-05) и повторяется на приёмке каждого этапа, изменившего схему базы.
3. В отчёте этапа приводится измеренное время восстановления и измеренная потеря данных.

Копия считается существующей только после успешного восстановления из неё. Наличие файла копией не считается.

## 11. Среды

Сред три. **Первая — основная на всё время разработки:** сервера организации сейчас нет и в ближайшее время не будет, поэтому этапы 0–7 строятся и принимаются локально.

### 11.1. Локальная среда исполнителя — первоклассная, а не временная

| Свойство | Значение |
|---|---|
| Где | Машина Держателя контракта: Apple Mac16,10, 10 ядер, 16 ГБ памяти, 872 ГБ свободно на SSD (Д-25 — факт, не допущение) |
| Чем поднимается | `./deploy/local/preflight.sh`, затем `./deploy/local/up.sh` — из пустого состояния |
| **Память виртуальной машины Docker** | **10,5 ГБ, задаётся вручную.** По умолчанию Docker Desktop отдаёт около 8,3 ГБ, чего не хватает: проверяется локальным preflight и является условием запуска (§ 0 `12-ЭКСПЛУАТАЦИЯ.md`) |
| Профиль пределов и ресурсов | `DEPLOY_PROFILE = local` (§ 6, § 7) |
| `BASE_URL` по умолчанию | `http://localhost:8080` |
| Второе имя для проверки переезда | `http://coes2.localhost:8080` — имена в зоне `localhost` разрешаются браузером в `127.0.0.1` без правки файлов и без записей DNS |
| Обратный прокси | **отсутствует** |
| Сертификаты, удостоверяющий центр, ACME | **отсутствуют и не нужны** |
| Внешняя сеть | не требуется ни для одного приёмочного сценария этапов 0–7 |
| Состав | те же образы, что и на сервере: PostgreSQL с PostGIS, API, обработчик, LibreOffice, LiveKit с Egress и Redis (этап 7) |

**Почему локально не нужен TLS, и почему поднимать его запрещено.** Браузер считает `localhost` и любое имя в зоне `localhost` доверенным контекстом. Из этого прямо следует:

- камера и микрофон доступны по обычному `http://localhost` — этап 7 проверяется локально полностью;
- служебный работник, веб-сокеты и все прочие возможности, требующие доверенного контекста, работают;
- cookie сессии: **атрибут `Secure` не выставляется, когда узел — `localhost`, `127.0.0.1` или имя в зоне `localhost`; во всех остальных случаях он обязателен**. Запуск с `BASE_URL`, начинающимся с `http://`, и узлом вне этого перечня отклоняется при старте с сообщением «Работа по HTTP вне localhost запрещена» (`05-ДОСТУП.md` § 10.3).

Поднимать локально удостоверяющий центр, самоподписанные сертификаты или локальный сервер ACME **запрещено**: это работа без результата.

**Все приёмочные сценарии этапов 0–7 обязаны проходить в этой среде** — без сервера, без домена, без внешней сети. Сценарии, у которых есть серверная часть, разделены: локальная часть входит в ворота этапа, серверная вынесена в этап В (`10-ЭТАПЫ.md` § 11) и ворота этапов 0–7 не блокирует.

**Нормативы производительности локально не проверяются** — только измеряются и записываются как справочные, со сторожевым порогом в десятикратное превышение (§ 8). Их место — этап В на сервере. Пытаться подтвердить бюджеты на ноутбуке не нужно и запрещено выдавать за подтверждение.

### 11.2. Рабочая среда (сервер организации)

Появляется вместе с сервером. `docker compose -f deploy/compose/compose.prod.yml`, обратный прокси, автоматический сертификат, имя из `BASE_URL`. Развёртывание и эксплуатация — `12-ЭКСПЛУАТАЦИЯ.md`. До появления сервера **файлы этой среды существуют в репозитории с этапа 0 и проверяются локально**: `deploy/install.sh`, `compose.prod.yml` и шаблон конфигурации прокси обязаны проходить проверку синтаксиса и разбор в составе `pnpm verify`. Развёртывание, которое впервые собирают в день появления сервера, ломается в этот же день.

### 11.3. Тестовая среда (сервер организации)

Тот же сервер, отдельная сеть, отдельные тома, отдельные порты, отдельное имя. Появляется вместе с рабочей. Тестовая среда **никогда** не обращается к рабочей базе и рабочим томам; разделение обеспечено разными именами томов и разными сетями, а не договорённостью.

Порядок на сервере: сначала обновление и проверка на тестовой среде, затем перенос в рабочую.
