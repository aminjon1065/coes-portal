# 05. Модель доступа

Документ старше `04-ДАННЫЕ.md`, `03-АРХИТЕКТУРА.md` и всех документов об интерфейсе (`00-КОНТРАКТ.md` § 3): ошибка в разграничении доступа не видна на экране и обнаруживается только последствиями.

---

## 1. Субъект действия — назначение, а не человек

Один человек может занимать несколько должностей одновременно, в том числе в разных подразделениях (это норма для государственного органа). Поэтому:

- **Человек** (`org.person`) — кто это.
- **Учётная запись** (`iam.account`) — чем он входит. Одна учётная запись на человека.
- **Назначение** (`org.assignment`) — человек на должности в подразделении, с датами.
- **Субъект прав — назначение.** Роли выдаются назначению, а не человеку. Область видимости определяется подразделением назначения.

Сессия всегда имеет **ровно одно активное назначение** (`iam.session.active_assignment_id`). Пользователь с двумя назначениями переключает рабочий контекст явно, кнопкой в шапке. Молчаливого объединения прав двух должностей не существует: это лишило бы журнал смысла.

**В журнал действий записывается, в каком назначении совершено действие.**

## 2. Разрешения

### 2.1. Правило разделения

**Перечень разрешений — код. Роли и состав разрешений в роли — данные.**

Каждому разрешению соответствует ветвь программы и проверка. Создать новое разрешение из экрана администрирования нельзя — ему не соответствовало бы ничего. Создать новую роль и собрать её из существующих разрешений — можно и нужно (Д-10: должности нам неизвестны).

Перечень объявлен в `packages/contracts/permissions.ts`, переносится в `access.permission` миграцией, в интерфейсе доступен только для чтения.

### 2.2. Формат кода

`<модуль>.<объект>.<действие>` — только строчные латинские буквы, точки и подчёркивание.

## 4. Область видимости

### 4.1. Точная формулировка

Пусть сессия имеет активное назначение `A`. Обозначим:

- `U(A)` — подразделение назначения `A`;
- `path(X)` — путь подразделения `X` в дереве (`org.org_unit.path`, тип `ltree`);
- `D(A)` — множество действующих замещений, в которых `A` является замещающим (дата действия включает текущую дату, `is_revoked = false`);
- `G(A)` — множество действующих разрешений области (`access.scope_grant`) назначения `A`.

**Область видимости сессии `S(A)` определяется так:**

1. Если в `G(A)` есть разрешение вида `all_regions` — `S(A)` = все подразделения. Конец.
2. Иначе `S(A)` = объединение:
   - `{ X : path(X) начинается с path(U(A)) }` — собственное подразделение и всё поддерево под ним;
   - для каждого разрешения вида `extra_subtree` с подразделением `V` — `{ X : path(X) начинается с path(V) }`;
   - для каждого замещения `d ∈ D(A)` — область видимости замещаемого назначения, вычисленная по пунктам 1–2 **без учёта его собственных замещений** (запрет транзитивности, § 5).

**Объект виден сессии, если его подразделение-владелец входит в `S(A)`.** Подразделение-владелец для каждой сущности:

| Сущность | Подразделение-владелец |
|---|---|
| Событие | `incident.owner_org_unit_id` |
| Дежурная смена, суточная сводка | `org_unit_id` |
| Пострадавший | подразделение-владелец связанного события |
| Слой | `owner_org_unit_id`; при `is_shared = true` виден всем |
| Отчёт | подразделение назначения, сформировавшего отчёт |
| Документ, регистрация, задача, узел файлов, совещание | собственное поле `org_unit_id` |

### 4.2. Следствия, которые не нужно оговаривать особо

- **Центральный аппарат видит всё** — потому что путь корневого подразделения является началом пути любого другого. Отдельной ветви программы для этого нет.
- **Сотрудник области видит свою область и все районы внутри неё** — по тому же правилу.
- **Сотрудник района видит только свой район.**

### 4.3. Что видно всем независимо от области

- Справочники и их элементы.
- Слои с признаком `is_shared`.
- Шаблоны печатных форм.
- Оргструктура в части наименований подразделений и должностей (без карточек сотрудников других регионов).
- Собственные уведомления и собственный профиль.

### 4.4. Право «все регионы»

Выдаётся **точечно конкретному назначению** записью `access.scope_grant` с указанием того, кто выдал, когда и на каком основании. **Из должности не следует и ролью не выдаётся.** Разрешение `access.scope.manage`, позволяющее его выдать, есть только у `SYS_ADMIN`.

### 4.5. Реализация

Область видимости вычисляется **на каждый запрос**, без кэширования. Причина: отзыв прав, окончание замещения и блокировка учётной записи обязаны действовать немедленно. При 150 одновременных сессиях стоимость одного дополнительного запроса к базе несущественна.

Все запросы к спискам обязаны проходить через единственную функцию `applyScope(query, session)` в `apps/api/src/modules/access/public.ts`. Прямое построение запроса к таблице предметных данных в обход этой функции запрещено правилом линтера `coes/require-scope`: каждый файл `queries.ts` модулей 11–20 обязан использовать `applyScope` в каждой функции, возвращающей список.

## 5. Замещение

### 5.1. Что это

Временная передача полномочий **приказом**, с датой начала и датой окончания. Постоянной должности заместителя в этом смысле не существует: заместитель — это отдельная должность со своим назначением и своими правами.

```
org.delegation: delegator_assignment_id, delegate_assignment_id,
                started_on, ended_on, order_number (обязателен), reason, is_revoked
```

### 5.2. Правила

1. **Замещающий видит и то, что создано до начала замещения.** Иначе он не сможет работать.
2. **Действия записываются в журнал от имени замещающего** с указанием, кого он замещал и по какому приказу (`audit.event.person_id` = замещающий, `audit.event.delegation_id` = замещение). Запись от имени замещаемого разрушила бы прослеживаемость и запрещена.
3. **Транзитивность запрещена.** Если Б замещает А, а В замещает Б, то В не получает прав А. Реализация: при вычислении области видимости и прав по замещению собственные замещения замещаемого не учитываются (§ 4.1, пункт 2, третий подпункт).
4. Оформить замещение своего назначения может обладатель `org.delegation.create`. Оформить чужое — только `org.delegation.manage_any` в пределах своей области.
5. Замещение действует, только если обе стороны — действующие назначения. Прекращение назначения любой из сторон немедленно прекращает действие замещения.
6. Замещение можно отозвать досрочно (`is_revoked`). Уже совершённые действия остаются в журнале как есть.
7. Права замещающего = собственные разрешения ∪ разрешения замещаемого. Область видимости — по § 4.1.

### 5.3. Что видит пользователь

Если у активного назначения есть действующие замещения, в шапке отображается пометка «Замещает: <должность>, приказ №<номер>». Скрытого замещения не бывает.

## 6. Две должности и переключение контекста

- Переключатель находится в шапке и показывает наименование текущей должности и подразделения.
- Переключение меняет `iam.session.active_assignment_id`, порождает запись в журнале и **полностью перезагружает данные экрана**: права и область видимости другие.
- Незавершённая форма при переключении не теряется без предупреждения: показывается диалог подтверждения.
- Если у человека одно назначение, переключатель не показывается, но должность в шапке отображается всегда.

## 7. Поведение при отказе

Различаются **три** случая. Смешивать их запрещено.

| Случай | Ответ API | Что показывает интерфейс |
|---|---|---|
| Объект не существует | `404 NOT_FOUND` | «Объект не найден. Возможно, он удалён или ссылка неверна.» |
| Объект существует, но вне области видимости | `403 ACCESS_DENIED` | «Этот объект существует, но не входит в вашу область видимости. Если доступ необходим для работы, обратитесь к администратору региона.» |
| Объект виден, но нет разрешения на действие | `403 ACCESS_DENIED` с `details.permission` | «Действие «<наименование действия>» недоступно для должности «<наименование должности>».» |

**Принятое решение и его цена.** Отказ вместо пустого результата подтверждает существование объекта. Это осознанный обмен: пользователь государственного органа должен понимать, что данные есть и ему их не показали, а не считать, что данных нет. Цена — по прямой ссылке можно установить факт существования объекта, не узнав о нём ничего иного. Запись о решении — `adr/11-otkaz-vmesto-pustogo-spiska.md`.

**Важное исключение.** В **списках** объекты вне области видимости не показываются и не считаются: список, наполовину состоящий из отказов, бесполезен. Правило отказа действует при **прямом обращении к объекту**.

**В интерфейсе действие, на которое нет разрешения, не показывается.** Кнопка отсутствует, а не показывается неактивной: неактивная кнопка сообщает о существовании возможности, которой у пользователя нет и не будет. Исключение — действия, недоступные из-за состояния объекта (например, «Закрыть» для уже закрытого события): такие показываются неактивными с подсказкой о причине.

Проверка прав на сервере обязательна **всегда**, независимо от того, что показывает интерфейс.

## 8. Персональные данные граждан

Отдельный правовой режим (Д-03), не совпадающий с режимом служебной информации.

### 8.1. Четыре уровня доступа

| Уровень | Кто | Что видит |
|---|---|---|
| 0 | Все, кто видит событие | Только числа в карточке события: погибло, травмировано, пропало без вести, эвакуировано |
| 1 | `pdn.person.read_depersonalized` | Список записей о пострадавших без идентифицирующих полей: состояние, возрастная группа, пол, степень тяжести |
| 2 | `pdn.person.read_identity` | Фамилия, имя, отчество, дата рождения, документ, адрес, сведения о состоянии здоровья |
| 3 | `pdn.person.export_identity` | Выгрузка сведений в открытом виде в файл |

### 8.2. Технические меры

1. **Разграничение обеспечивается правами базы данных, а не проверкой в программе.** Основная роль `coes_app` не имеет права `SELECT` на столбцы `last_name`, `first_name`, `middle_name`, `birth_date`, `document_number`, `address`, `health_note`. Модуль `pdn` при наличии разрешения уровня 2 использует отдельное соединение под ролью `coes_pdn`.
2. Использование соединения `coes_pdn` разрешено **только** из `apps/api/src/modules/pdn/**` — правилом линтера.
3. Обезличенные столбцы (`age_group`, `sex_public`, `health_category_item_id`) поддерживаются триггером и доступны основной роли.
4. Аналитика **не имеет** доступа к идентифицирующим столбцам по правам базы. Обезличивание в отчётах не является добросовестностью программы — оно обеспечено невозможностью.

### 8.3. Минимизация состава

Хранится минимально необходимое. Возраст хранится группой (`0-6`, `7-17`, `18-59`, `60+`, `unknown`), а не числом. Добавление нового идентифицирующего поля — изменение контракта с записью о решении.

### 8.4. Журналирование чтения

**Чтение уровня 2 и выше пишется в журнал действий отдельной записью** — в отличие от обычных чтений, которые не журналируются (§ 9.2). Запись содержит: кто, в каком назначении, какие записи, по какому событию, когда.

### 8.5. Выгрузка

- Выгрузка уровня 3 требует указания **цели и основания** в диалоге. Текст сохраняется в `access.foreign_access` и в журнале.
- Любая другая выгрузка (реестр событий, отчёт, перекрёстная таблица) **автоматически обезличена**: идентифицирующие поля в неё не попадают, потому что формирующий её код работает под ролью `coes_app`.

### 8.6. Срок хранения и обезличивание

- Настройка `PDN_RETENTION_YEARS`, начальное значение 5, точка отсчёта — закрытие события.
- По истечении срока запись **не удаляется**. Задание помечает её к обезличиванию; оператор персональных данных или архивист утверждает акт обезличивания (`pdn.person.depersonalize`); только после этого идентифицирующие столбцы обнуляются.
- Обезличенные столбцы сохраняются навсегда: статистика прошлых лет не должна разрушаться от истечения срока хранения персональных данных.
- Акт обезличивания хранится постоянно.

### 8.7. Доступ администратора к чужому содержимому

**Администратор не читает содержимое переписки, документов, файлов и карточек событий.** Это обеспечено составом ролей (§ 3.1), а не обещанием.

Когда доступ действительно необходим (расследование, поручение руководства, восстановление данных), действует отдельная процедура:

```
access.foreign_access (id, requester_person_id, requester_assignment_id,
                       target_schema, target_table, target_id,
                       purpose text not null, basis text not null,
                       requested_at, approved_by_person_id, approved_at,
                       valid_until timestamptz, revoked_at)
```

1. Обращение создаёт обладатель `system.content.read_foreign` с обязательным указанием **цели** и **основания** (номер поручения, номер служебной записки).
2. Обращение утверждает **другое лицо** с тем же разрешением. Самоутверждение запрещено ограничением.
3. Срок действия — не более `FOREIGN_ACCESS_MAX_HOURS` (начальное значение 72).
4. Каждое обращение к данным в рамках доступа пишет запись в журнал.
5. **Владелец данных немедленно получает уведомление**: кто, когда, к чему обратился и на каком основании. Уведомление не отключается и не скрывается.

## 9. Журнал действий

### 9.1. Что записывается обязательно

- Любое действие, изменяющее данные: создание, изменение, смена состояния, удаление.
- Вход, выход, неудачная попытка входа, блокировка, смена пароля, выдача одноразового кода.
- Переключение рабочего контекста.
- Выдача и отзыв роли, области, замещения.
- Чтение персональных данных уровня 2 и выше.
- Чтение текста удалённого сообщения.
- Любое обращение в рамках доступа к чужому содержимому.
- Выгрузка данных в файл.
- Изменение настройки или предела.

### 9.2. Что не записывается и почему

Обычные чтения (открытие реестра, карточки, панели) **не журналируются**. Причина: при 150 одновременных пользователях это дало бы миллионы записей в сутки, в которых утонули бы записи об изменениях. Журнал должен оставаться читаемым спустя годы.

Это решение записано осознанно. Условие пересмотра: требование Комитета журналировать доступ к сведениям определённой категории — тогда журналирование чтения включается для этой категории, как уже сделано для персональных данных.

### 9.3. Свойства журнала

- **Только добавление.** Роль `coes_app` не имеет прав `UPDATE` и `DELETE` на `audit.event`.
- **Цепочка хешей.** Каждая запись содержит хеш предыдущей. Изъятие или подмена записи обнаруживается командой `pnpm audit:verify`, которая сообщает номер первой нарушенной связи.
- **Одна транзакция.** Запись журнала пишется в той же транзакции, что и изменение. Журнал не может разойтись с данными.
- **Ровно одна запись на изменяющее действие.** Метод API, не породивший записи, — дефект.
- **Хранение постоянное.** Журнал не подпадает под сроки хранения документов и не уничтожается.
- **Снимок значений.** Сохраняется `entity_label` — регистрационный номер или наименование на момент действия, а также `before_data` и `after_data`. Журнал читается без обращения к текущему состоянию объекта.

### 9.4. Кто что видит

| Кто | Что |
|---|---|
| Любой, кто видит объект | Лента журнала в карточке этого объекта: кто, когда, что изменил |
| `audit.event.read_all` | Экран журнала целиком с фильтрами по человеку, действию, объекту, периоду |
| `audit.event.verify` | Запуск проверки целостности |
| Владелец данных | Уведомления об обращениях к его данным (§ 8.7) |

Журнал нельзя выгрузить в открытом виде без разрешения `audit.event.read_all`.

## 10. Вход, пароли, сессии

### 10.1. Учётные записи

- Самостоятельной регистрации нет. Учётную запись создаёт `SYS_ADMIN` или `REGION_ADMIN`.
- Один человек — одна учётная запись. Общих и обезличенных учётных записей («дежурный», «канцелярия») **не бывает**: они разрушают прослеживаемость. При попытке создать вторую учётную запись на одного человека система отказывает.
- Учётная запись без действующего назначения войти не может: субъектом прав является назначение.

### 10.2. Пароли

- Хеширование: Argon2id. Хранение открытых паролей и обратимого шифрования запрещено.
- Минимальная длина — 12 символов (`PASSWORD_MIN_LENGTH`). Проверка по списку 10 000 наиболее распространённых паролей.
- Первый вход после создания учётной записи требует смены пароля.
- Восстановление — только через администратора: он выдаёт одноразовый код, действующий `PASSWORD_RESET_TTL_MIN` (начальное значение 60) минут. Ссылок по электронной почте не существует даже при наличии почтового сервера: почтовый ящик не является доверенным каналом в закрытом контуре (Д-05).
- **Принудительная смена пароля по расписанию не реализуется.** Причина: вынуждает выбирать предсказуемые последовательности и снижает стойкость. Условие возврата: письменное требование регламента Комитета; тогда добавляется настройка срока действия пароля.
- Двухфакторная проверка не реализуется (`01-ПРОДУКТ.md` § Не строим): СМС и звонки исключены условием задачи, аппаратных ключей у сотрудников нет.

### 10.3. Сессии

- Серверные сессии в PostgreSQL. Cookie: `HttpOnly`, `Secure`, `SameSite=Strict`, путь `/`.
- Предельный срок сессии — `SESSION_MAX_HOURS` (начальное значение 12). Срок бездействия — `SESSION_IDLE_MIN` (начальное значение 60).
- Защита от подделки межсайтовых запросов: помимо `SameSite=Strict`, каждый изменяющий запрос обязан содержать заголовок `X-CSRF-Token`, совпадающий со значением отдельной cookie. Несовпадение — отказ.
- Одновременных сессий на учётную запись — не более `LIMIT_SESSION_PER_ACCOUNT` (начальное значение 5); при превышении закрывается самая старая, пользователь уведомляется.
- Блокировка учётной записи немедленно закрывает все её сессии.
- Прекращение назначения немедленно делает сессию с этим активным назначением недействительной.
