# 00. Контракт

Это корневой документ комплекта. Он не описывает систему — он описывает, **как читать остальные документы и что делать при противоречии**.

Комплект является контрактом на постройку внутренней рабочей платформы Комитета по чрезвычайным ситуациям и гражданской обороне Республики Таджикистан. Исполнитель строит систему строго по этим документам. То, чего в них нет, не строится. То, что в них описано, строится буквально.

---

## 1. Держатель контракта

**Держатель контракта** — единственное лицо, разрешающее противоречия, утверждающее изменения контракта и принимающее этапы.

Держатель контракта — постановщик задачи (владелец репозитория). Прямого канала связи с Комитетом нет ни у кого. Это означает:

- Никто не придёт и не поправит неверное допущение. Ошибка обнаружится при внедрении.
- Исполнителю **запрещено** самостоятельно разрешать неоднозначность, даже очевидную. Порядок действий описан в `11-ИСПОЛНИТЕЛЬ.md`, раздел «Что делать при неоднозначности».
- Любое изменение контракта оформляется записью о решении в `adr/` и утверждается Держателем контракта.

## 2. Четыре принципа

Принципы старше любого другого документа комплекта. У каждого есть механизм, который ломает сборку при нарушении. Принцип без механизма забывается на третьем экране.

### П-1. Архитектура переживает ошибку в допущениях о заказчике

Мы не видели ни одного нормативного документа Комитета. Значит классификаторы, формы, сроки, номенклатура, оргструктура и роли, которые мы придумали, **почти наверняка неверны**. Система обязана это пережить без участия программиста.

**Что обязано быть данными в базе с экраном администрирования, а не кодом:**

| Сущность | Кто меняет | Документ |
|---|---|---|
| Виды событий и признак отнесения к ЧС | Администратор системы | `04-ДАННЫЕ.md` § Справочники |
| Масштабы, причины, ведомства, типы ущерба | Администратор системы | `04-ДАННЫЕ.md` § Справочники |
| Состав дополнительных полей карточки по виду события | Администратор системы | `04-ДАННЫЕ.md` § Расширяемая часть |
| Шаблоны печатных и отчётных форм | Делопроизводитель | `04-ДАННЫЕ.md` § Шаблоны |
| Сроки хранения, точки отсчёта, действия по истечении | Архивист | `04-ДАННЫЕ.md` § Хранение |
| Номенклатура дел | Архивист | `04-ДАННЫЕ.md` § Канцелярия |
| Шаблоны регистрационных номеров | Делопроизводитель | `04-ДАННЫЕ.md` § Нумерация |
| Оргструктура, должности, назначения, замещения | Администратор системы или региона | `05-ДОСТУП.md` |
| Роли и состав разрешений в роли | Администратор системы | `05-ДОСТУП.md` § Роли |
| Числовые пределы работы системы | Администратор системы | `03-АРХИТЕКТУРА.md` § Реестр пределов |

**Что остаётся кодом и данными не является** (потому что каждой единице соответствует ветвь программы, которую нельзя создать из экрана администрирования):

- Перечень **разрешений** (`permission`). Роль — данные, набор разрешений в роли — данные, сам перечень возможных разрешений — код.
- Перечень **состояний** жизненных циклов и допустимые переходы между ними.
- Перечень **архетипов экранов** и компонентов библиотеки.

**Правило замещаемости (обязательное):**

> Ни одна ветвь логики не сравнивает значение кода элемента справочника. Ветвление допустимо только по булевым или перечислимым **признакам** элемента справочника, объявленным в схеме.

Пример запрещённого кода: `if (incident.kind.code === 'ZML-01')`.
Пример разрешённого кода: `if (incident.kind.requiresCasualtyBlock)`.

**Механизм проверки:** `pnpm check:literals` — сканирует `apps/api/src`, `apps/web/src`, `apps/worker/src` на строковые литералы, совпадающие с шаблоном кода справочника `^[A-ZА-Я]{2,5}(-[0-9A-Z]{1,4})+$`, и завершается с ошибкой при любом совпадении вне каталога `packages/db/seed`. Проверка входит в `pnpm verify`.

### П-2. Один язык, один контракт, невозможность расхождения

Документация расходится с кодом там, где расхождение не является ошибкой сборки. Поэтому:

- Схема базы данных описана нумерованными SQL-файлами и является источником истины. Типы TypeScript **генерируются** из живой схемы (`pnpm db:types`).
- Форма запроса и ответа каждого метода API описана один раз в `packages/contracts` и используется одновременно серверной проверкой, клиентом и файлом OpenAPI.
- `pnpm verify` завершается с ошибкой, если сгенерированные типы или OpenAPI отличаются от закоммиченных.

**Следствие для документов:** `04-ДАННЫЕ.md` и `09-API.md` описывают **намерение и правила**; расхождение между ними и сгенерированными артефактами является дефектом документа либо кода и подлежит устранению в том же изменении.

### П-3. Исполнителю нечего изобретать в интерфейсе

Предыдущая попытка развалилась визуально, потому что композиционные решения принимались заново на каждом экране. Поэтому:

- Экран собирается **только** из архетипа (`08-ЭКРАНЫ.md`) и компонентов библиотеки (`07-КОМПОНЕНТЫ.md`).
- Собственная вёрстка на экранах запрещена физически.

**Механизм проверки:** правило ESLint `coes/no-intrinsic-jsx` — в `apps/web/src/screens/**` и `apps/web/src/features/**` запрещены встроенные HTML-элементы (`div`, `span`, `table`, `p`, `button` и любые другие имена в нижнем регистре), атрибут `style`, атрибут `className`. Разрешены только компоненты, импортированные из `@coes/ui`, и фрагменты `<>`. Единственное место, где встроенные элементы разрешены, — `packages/ui/src`.

Дополнительно: снимки экрана витрины компонентов (`/__ui`) сравниваются с эталоном с допуском 0,1 % площади.

### П-4. Готовность не измеряется. Сценарий проходит или не проходит

- Процентов готовности не существует. Ни в отчётах, ни в документах, ни в разговоре.
- Каждый приёмочный сценарий существует в двух видах: пошаговый на русском языке для Держателя контракта и автоматический тест с тем же номером.
- Реализация, спрятанная за флагом «выключено по умолчанию», считается отсутствующей реализацией и является нарушением контракта.
- Настройка с несколькими допустимыми значениями флагом не является **только если** каждое значение работает и покрыто тестом. Иначе это флаг.

## 3. Старшинство документов при противоречии

Если два документа комплекта противоречат друг другу, действует документ, стоящий выше в этом списке. Исполнитель обязан завести запись в `ВОПРОСЫ.md` и продолжить по старшему документу.

1. `00-КОНТРАКТ.md` — принципы
2. `02-ДОПУЩЕНИЯ.md` — если допущение опровергнуто фактом, оно старше любого решения, которое из него выведено
3. `01-ПРОДУКТ.md` — границы и раздел «Не строим»
4. `05-ДОСТУП.md` — безопасность и разграничение доступа старше удобства
5. `04-ДАННЫЕ.md` — целостность данных
6. `03-АРХИТЕКТУРА.md`
7. `09-API.md`
8. `06-ДИЗАЙН-СИСТЕМА.md` → `07-КОМПОНЕНТЫ.md` → `08-ЭКРАНЫ.md` (в этом порядке между собой)
9. `10-ЭТАПЫ.md`
10. `12-ЭКСПЛУАТАЦИЯ.md`

**Противоречие между документом и кодом:** прав документ. Код приводится в соответствие, либо заводится вопрос и работа по этой задаче останавливается.

**Противоречие внутри одного документа:** остановка задачи, запись в `ВОПРОСЫ.md`, ожидание Держателя контракта. Выбирать «более разумный» вариант запрещено.

## 4. Состав комплекта и что открывать когда

| Файл | Открывается когда |
|---|---|
| `00-КОНТРАКТ.md` | Перед началом любой работы; при любом противоречии |
| `01-ПРОДУКТ.md` | Когда неясно, входит ли задача в объём |
| `02-ДОПУЩЕНИЯ.md` (живой) | Перед этапом внедрения; при получении любого факта о Комитете |
| `03-АРХИТЕКТУРА.md` | При создании модуля, сквозного механизма, при работе с пределами и нормативами |
| `04-ДАННЫЕ.md` | При создании или изменении любой таблицы |
| `05-ДОСТУП.md` | При любой проверке прав, при работе с персональными данными и журналом |
| `06-ДИЗАЙН-СИСТЕМА.md` | Перед первой строкой стилей; при любом вопросе о цвете, размере, тексте |
| `07-КОМПОНЕНТЫ.md` | При создании или использовании компонента |
| `08-ЭКРАНЫ.md` | При создании любого экрана |
| `09-API.md` | При создании любого метода API |
| `10-ЭТАПЫ.md` | В начале и в конце каждого этапа |
| `11-ИСПОЛНИТЕЛЬ.md` | Ежедневно; перед отчётом; при неоднозначности |
| `12-ЭКСПЛУАТАЦИЯ.md` | При работе с развёртыванием, копированием, сертификатами |
| `13-ГЛОССАРИЙ.md` | При выборе любого имени |
| `ВОПРОСЫ.md` (живой) | Когда возникла неоднозначность |
| `adr/` | При принятии решения, у которого был выбор |

**Живых документов ровно два:** `02-ДОПУЩЕНИЯ.md` и `ВОПРОСЫ.md`. Плюс каталог `adr/`, который только пополняется.

Создание любых других документов запрещено. В частности запрещены: реестры готовности, матрицы состояния, дорожные карты, отчёты о самопроверке, файлы состояния проекта, сводки прогресса.

## 5. Что запрещено без записи о решении и утверждения Держателем контракта

- Замена любого компонента стека из `03-АРХИТЕКТУРА.md`.
- Добавление нового постоянно работающего процесса или службы.
- Изменение границ модуля или правил их взаимодействия.
- Изменение модели доступа, состава разрешений, поведения при отказе.
- Изменение любого значения токена дизайн-системы.
- Изменение приёмочного сценария.
- Реализация чего-либо, не описанного в комплекте.

## 6. Единицы, форматы, язык

- Язык интерфейса, документов, сообщений об ошибках, комментариев в коде и отчётов — **русский**. Второго языка нет.
- Идентификаторы в коде и в базе данных — **английские**, по глоссарию (`13-ГЛОССАРИЙ.md`).
- Часовой пояс отображения — `Asia/Dushanbe` (UTC+5, перехода на летнее время нет). Хранение и передача — UTC.
- Денежная единица — сомони (`TJS`), обозначение в интерфейсе `смн`.
- Форматы дат, чисел и координат — `06-ДИЗАЙН-СИСТЕМА.md` § Форматы.
