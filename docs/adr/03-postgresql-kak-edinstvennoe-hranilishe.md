# 03. PostgreSQL как единственное хранилище состояния

**Дата:** 2026-09-08
**Состояние:** принято

## Вопрос
Где хранить сессии, очередь фоновых заданий, шину событий между процессами и поисковый указатель.

## Решение
Всё в PostgreSQL: сессии — таблица, очередь — `pg-boss`, шина — `LISTEN/NOTIFY`, поиск — полнотекстовый указатель. Отдельных служб хранения состояния нет.

Единственное исключение: Redis появляется на этапе 7 как служебная зависимость LiveKit Egress. Он не хранит состояния приложения, не входит в контур резервного копирования, его потеря прерывает только текущую запись.

## Отвергнуто
- **Redis для сессий и очередей** — второй компонент с состоянием, второй контур резервного копирования, вторая точка отказа. При 150 одновременных сессиях выигрыш отсутствует.
- **RabbitMQ, Kafka** — не оправданы при этой нагрузке ни в какой мере.
- **Elasticsearch, OpenSearch, Meilisearch** — третья служба с собственной памятью и собственной копией данных при потолке 32 ГБ.

## Последствия
Проще: одна резервная копия восстанавливает систему целиком; системный администратор обслуживает одну базу; согласованность данных и очереди в одной транзакции.
Сложнее: нагрузка на базу выше; `LISTEN/NOTIFY` ограничен 8000 байтами полезной нагрузки, поэтому по шине передаются только вид события и идентификатор.
Платим: полнотекстовый поиск беднее специализированного.

## Условие пересмотра
p95 поиска превышает 500 мс при более чем 2 000 000 объектов, либо очередь фоновых заданий устойчиво превышает 10 000 записей.
