# 08. Собственная библиотека компонентов вместо готового набора

**Дата:** 2026-09-08
**Состояние:** принято

## Вопрос
Предыдущая попытка развалилась визуально: единой библиотеки не существовало, и исполнитель изобретал вёрстку на каждом экране. Как сделать изобретение невозможным.

## Решение
Собственная закрытая библиотека в `packages/ui` на примитивах Radix UI (доступность, работа с клавиатурой) и CSS Modules с токенами в переменных CSS. Полный каталог компонентов со всеми состояниями — `07-КОМПОНЕНТЫ.md`.

Запрет обеспечен машинно: правило `coes/no-intrinsic-jsx` запрещает встроенные HTML-элементы, атрибуты `style` и `className` везде, кроме `packages/ui/src`. Витрина компонентов сравнивается со снимками эталона с допуском 0,1 %.

## Отвергнуто
- **Material UI, Ant Design и подобные наборы** — приносят чужой визуальный язык, а переопределения расползаются по экранам; закрыть набор от изменения на экране невозможно.
- **Утилитарные классы (Tailwind) на экранах** — это и есть изобретение вёрстки на каждом экране, то есть буквальное повторение второго провала.
- **Storybook как витрина** — отдельная сборка и отдельная зависимость ради того, что даёт обычная страница приложения.
- **Полностью собственные примитивы без Radix** — пришлось бы самостоятельно писать управление фокусом, клавиатурой и доступностью; ошибки в этом не видны на экране.

## Последствия
Проще: интерфейс однороден по построению, а не по старанию; изменение токена меняет систему целиком.
Сложнее: каждый нужный компонент приходится описать в каталоге до применения.
Платим: компонента, которого нет в каталоге, не существует; его появление — вопрос Держателю контракта.

## Условие пересмотра
Не предполагается. Ослабление правила `no-intrinsic-jsx` означает возврат к причине второго провала.
