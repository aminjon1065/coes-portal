# 04. Kysely и SQL-миграции вместо ORM

**Дата:** 2026-09-08
**Состояние:** принято

## Вопрос
Как обращаться к базе, если нужны пространственные типы, полнотекстовый поиск, рекурсивные запросы по дереву подразделений, оконные функции для аналитики и права на уровне столбцов.

## Решение
Схема — нумерованные SQL-файлы, единственный источник истины. Обращения — через типизированный построитель запросов Kysely. Типы TypeScript генерируются из живой схемы `kysely-codegen`.

## Отвергнуто
- **Prisma** — слабая поддержка PostGIS (пространственные типы попадают в «неподдерживаемые»), собственный файл схемы становится вторым источником истины, миграции ограничены.
- **TypeORM** — непредсказуемое поведение миграций, скрытые запросы.
- **Чистый SQL без построителя** — нет проверки типов на компиляции, а человека, вычитывающего запросы, нет.
- **Хранимые процедуры как основной способ** — логика уходит в базу, где её не покрывают тесты и не видит система типов.

## Последствия
Проще: любая возможность PostgreSQL доступна; схема читается как схема; типы не могут разойтись с базой.
Сложнее: запросы пишутся вручную, отношения не подгружаются автоматически.
Платим: больше строк на выборку связанных данных.

## Условие пересмотра
Не предполагается. Замена построителя не влияет на схему и может быть выполнена помодульно.
