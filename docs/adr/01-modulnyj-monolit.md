# 01. Модульный монолит вместо микросервисов и слоистой архитектуры

**Дата:** 2026-09-08
**Состояние:** принято

## Вопрос
Как разделить систему из двадцати модулей так, чтобы границы были видны и не размывались, при одном сервере, одном автономном исполнителе и отсутствии человека, читающего код.

## Решение
Модульный монолит, feature-first. Одно приложение API, один фоновый обработчик, одно веб-приложение. Модули пронумерованы; модуль импортирует только из модулей с меньшим номером и только через `public.ts`. Границы проверяются `dependency-cruiser` в составе `pnpm verify`. Циклы разрешаются на стороне веб-приложения, а не в API.

Развязка «порт — адаптер» применяется только в двух местах: хранилище двоичных объектов и медиасервер.

## Отвергнуто
- **Микросервисы** — распределённые транзакции в документообороте с версионированием при отсутствии человека для отладки распределённых отказов. Один сервер делает разнесение бессмысленным.
- **Слоистая архитектура (контроллеры, сервисы, репозитории)** — границы предметных областей не видны в структуре, всё стекается в общую папку сервисов. Первая попытка провалилась именно так.
- **Чистая и гексагональная целиком** — объём переходников на автономном исполнителе превышает объём полезного кода.
- **Событийная архитектура, CQRS** — нагрузка на чтение и запись сопоставима, аналитика работает на тех же данных.

## Последствия
Проще: одна транзакция, одна база, один отладочный контур, одна резервная копия восстанавливает всё.
Сложнее: один процесс — одна точка отказа. Компенсируется отсутствием состояния в процессе: число экземпляров увеличивается настройкой.
Платим: модули нельзя разнести по серверам без переделки. При одном сервере это не ограничение.

## Условие пересмотра
Одновременно: число одновременных сессий устойчиво превышает 500 **и** один модуль потребляет более 60 % процессорного времени. Первым выносится медиа- и файловая часть, а не разрезание предметных модулей.
