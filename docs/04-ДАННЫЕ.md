# 04. Модель данных

Источник истины по схеме — нумерованные SQL-файлы в `packages/db/migrations`. Этот документ описывает **намерение, правила и жизненные циклы**. Расхождение между документом и схемой является дефектом и устраняется тем же изменением.

---

## 1. Правила именования

| Что | Правило | Пример |
|---|---|---|
| Схема | Совпадает с именем модуля | `incident` |
| Таблица | Единственное число, snake_case | `org_unit`, `catalog_item` |
| Колонка | snake_case | `occurred_at` |
| Внешний ключ | `<таблица>_id` | `kind_item_id` |
| Булево | `is_*` или `has_*` | `is_emergency` |
| Отметка времени | `*_at`, тип `timestamptz` | `registered_at` |
| Дата без времени | `*_date`, тип `date` | `duty_date` |
| Перечисление | Собственный тип `<схема>.<имя>_enum` | `incident.status_enum` |
| Индекс | `ix_<таблица>__<колонки>` | `ix_incident__occurred_at` |
| Уникальный индекс | `ux_<таблица>__<колонки>` | `ux_incident__reg_number` |
| Ограничение | `ck_<таблица>__<смысл>` | `ck_incident__counts_non_negative` |

Русские наименования сущностей — `13-ГЛОССАРИЙ.md`. Синонимы запрещены: если в глоссарии написано «событие», нигде не может быть «происшествие», «инцидент» или «случай».

## 2. Обязательные колонки

Каждая таблица предметных данных содержит:

```sql
id            uuid        primary key,
created_at    timestamptz not null default now(),
created_by_person_id uuid null references org.person(id),
updated_at    timestamptz not null default now(),
updated_by_person_id uuid null references org.person(id),
version       integer     not null default 1
```

- `version` увеличивается на единицу при каждом изменении, обеспечивает обнаружение одновременного изменения (`03-АРХИТЕКТУРА.md` § 5.5).
- `created_by_person_id` допускает `NULL` только для строк начального наполнения.
- Справочные и служебные таблицы (`ref.*`, `sys.*`) содержат тот же набор.
- Таблица `audit.event` — исключение: у неё нет `updated_*` и `version`, потому что изменение записи журнала невозможно.

## 3. Идентификаторы и нумерация

### 3.1. Первичные ключи

`uuid` версии 7, формируется приложением. Пользователю не показывается никогда: в интерфейсе объект опознаётся регистрационным номером или наименованием.

### 3.2. Грамматика шаблона регистрационного номера

Шаблон — настройка (`sys.setting`), не константа.

| Подстановка | Значение |
|---|---|
| `{ГГГГ}` | Год, 4 цифры |
| `{ГГ}` | Год, 2 цифры |
| `{ММ}` | Месяц, 2 цифры |
| `{ДД}` | День, 2 цифры |
| `{N}` | Порядковый номер без ведущих нулей |
| `{N:4}` | Порядковый номер, дополненный нулями до 4 знаков |
| `{ПОДР}` | Код подразделения-владельца |
| `{РЕГ}` | Код региона верхнего уровня |
| Прочие символы | Переносятся как есть |

Начальные значения (временные, Д-15):

| Объект | Ключ настройки | Шаблон | Область счётчика | Пример |
|---|---|---|---|---|
| Событие | `NUMBER_TEMPLATE_INCIDENT` | `{ГГГГ}-{ПОДР}-{N:4}` | год + подразделение | `2026-DUS-0017` |
| Внутренний документ | `NUMBER_TEMPLATE_DOCUMENT` | `{ПОДР}/{N:3}-{ГГ}` | год + подразделение | `DUS/017-26` |
| Входящий | `NUMBER_TEMPLATE_INCOMING` | `вх-{N:4}/{ГГ}` | год | `вх-0231/26` |
| Исходящий | `NUMBER_TEMPLATE_OUTGOING` | `исх-{N:4}/{ГГ}` | год | `исх-0142/26` |
| Задача | `NUMBER_TEMPLATE_TASK` | `З-{ГГ}-{N:4}` | год | `З-26-0088` |
| Акт уничтожения | `NUMBER_TEMPLATE_DESTRUCTION_ACT` | `А-{ГГГГ}-{N:2}` | год | `А-2026-03` |

### 3.3. Выдача номеров

```sql
sys.number_sequence (
  scope_key   text primary key,   -- например 'incident:2026:DUS'
  next_value  bigint not null default 1
)
```

Номер выдаётся в той же транзакции через `SELECT ... FOR UPDATE`.

- Для событий, документов, задач и актов **пропуски в нумерации допустимы**: откат транзакции оставляет пропуск. Повторное использование номера запрещено.
- Для регистрации входящих и исходящих (`office.registration`) **пропуски недопустимы**: журнал канцелярии обязан быть непрерывным. Механизм: строка создаётся в состоянии `reserved` отдельной короткой транзакцией; при успехе переходит в `active`, при неудаче — в `void` с указанием причины. Аннулированный номер остаётся в журнале видимой строкой, как в бумажном журнале.

Смена шаблона не затрагивает уже присвоенные номера: они хранятся строкой.

### 4.2. Конфигурация полнотекстового поиска

```sql
CREATE TEXT SEARCH DICTIONARY tajik_unaccent (TEMPLATE = unaccent, RULES = 'tajik');
CREATE TEXT SEARCH CONFIGURATION russian_tj (COPY = russian);
ALTER TEXT SEARCH CONFIGURATION russian_tj
  ALTER MAPPING FOR word, hword, hword_part WITH tajik_unaccent, russian_stem;
```

Все столбцы `search_tsv` формируются через `to_tsvector('russian_tj', ...)`, тип `tsvector`, `GENERATED ALWAYS ... STORED`, индекс GIN. **Состав полей задан здесь и подразумеванию не подлежит:**

| Таблица | Выражение |
|---|---|
| `incident.incident` | `to_tsvector('russian_tj', coalesce(reg_number,'') \|\| ' ' \|\| title \|\| ' ' \|\| coalesce(description,'') \|\| ' ' \|\| coalesce(place_text,'') \|\| ' ' \|\| coalesce(weather_text,''))` |
| `geo.map_feature` | `to_tsvector('russian_tj', coalesce(label,''))` |
| `chat.message` | `to_tsvector('russian_tj', coalesce(body,''))` |
| `doc.document` | `to_tsvector('russian_tj', coalesce(reg_number,'') \|\| ' ' \|\| title)` |
| `office.registration` | `to_tsvector('russian_tj', coalesce(reg_number,'') \|\| ' ' \|\| coalesce(correspondent,'') \|\| ' ' \|\| coalesce(subject,''))` |
| `task.task` | `to_tsvector('russian_tj', coalesce(reg_number,'') \|\| ' ' \|\| title \|\| ' ' \|\| coalesce(description,''))` |
| `files.node` | `to_tsvector('russian_tj', name)` |

Добавление поля в поисковый столбец — изменение схемы и записи в этом документе одним изменением.

### 4.3. Нормализация для поиска по подстроке

```sql
CREATE FUNCTION public.tj_norm(t text) RETURNS text
LANGUAGE sql IMMUTABLE STRICT PARALLEL SAFE AS
$fn$ SELECT lower(public.unaccent('public.tajik_unaccent', t)) $fn$;
```

**Где применяется `tj_norm`.** Поиск по подстроке (не полнотекстовый) работает через вычисляемый столбец `<имя>_norm text GENERATED ALWAYS AS (public.tj_norm(<имя>)) STORED` с индексом `gin (<имя>_norm gin_trgm_ops)`. Столбцы, для которых он создаётся:

| Таблица | Исходные столбцы | Где используется |
|---|---|---|
| `org.person` | `last_name`, `first_name`, `middle_name` | Э-013 «Сотрудники», `PersonSelect` |
| `org.org_unit` | `name` | Э-010, `OrgUnitSelect` |
| `org.position` | `name` | Э-011, вкладка «Должности» |
| `ref.catalog_item` | `name` | `CatalogSelect`, Э-031 |
| `files.node` | `name` | Э файлового менеджера |
| `pdn.affected_person` | `last_name`, `first_name`, `middle_name` | Только под ролью `coes_pdn` |

**Какой механизм на каком экране.** Реестры событий, документов, задач, регистраций и поиск по переписке используют полнотекстовый столбец `search_tsv`. Выбор сотрудника, подразделения, должности, элемента справочника и поиск по имени файла используют `tj_norm` и поиск по подстроке. Третьего механизма нет.

**Обязательное правило.** Функция объявлена неизменяемой, чтобы участвовать в вычисляемых столбцах и индексах. Это накладывает запрет: **после появления данных файл `tajik.rules` изменять нельзя.** Изменение требует перестроения всех вычисляемых столбцов и индексов, зависящих от `tj_norm`, и оформляется отдельной миграцией с записью о решении.

### 4.4. Сортировка

```sql
CREATE COLLATION public.coll_tj (
  provider = icu,
  locale = 'ru-RU',
  rules = '&Г<ғ<<<Ғ &И<ӣ<<<Ӣ &К<қ<<<Қ &У<ӯ<<<Ӯ &Х<ҳ<<<Ҳ &Ч<ҷ<<<Ҷ',
  deterministic = true

```

Правила заданы явно и не зависят от наличия таджикских данных в библиотеке ICU. Сопоставление `coll_tj` применяется к столбцам: фамилия, имя, отчество, наименование подразделения, наименование должности, наименование населённого пункта, наименование элемента справочника, наименование файла и папки.

## 5. Справочники

Механизм, обслуживающий принцип П-1. Виды событий, масштабы, причины, дела, сроки и прочее — строки в этих двух таблицах.

```sql
ref.catalog (
  id                uuid primary key,
  code              text not null unique,      -- ИМЯ_СПРАВОЧНИКА, только буквы и подчёркивание
  name              text not null,
  description       text,
  is_hierarchical   boolean not null default false,
  is_system         boolean not null default false,
  attribute_schema  jsonb  not null default '[]',
  ...обязательные колонки
);

ref.catalog_item (
  id             uuid primary key,
  catalog_id     uuid not null references ref.catalog(id) on delete restrict,
  parent_id      uuid null references ref.catalog_item(id) on delete restrict,
  code           text not null,                -- КОД-ЭЛЕМЕНТА, обязан содержать дефис
  name           text not null collate public.coll_tj,
  short_name     text,
  sort_order     integer not null default 0,
  is_active      boolean not null default true,
  is_provisional boolean not null default false,
  valid_from     date,
  valid_to       date,
  attributes     jsonb not null default '{}',
  color_token    text null,
  ...обязательные колонки,
  unique (catalog_id, code)
);
```

### 5.1. Разделение «код справочника — код элемента»

Это разделение обеспечивает принцип П-1 и обязательно к соблюдению:

- **Код справочника** (`ref.catalog.code`, например `INCIDENT_KIND`) — часть программы. Программа знает, какие справочники существуют, и обращается к ним по коду. Формат: только заглавные латинские буквы и подчёркивание, **без дефиса**.
- **Код элемента** (`ref.catalog_item.code`, например `ZML-01`) — данные. Программа **никогда** его не сравнивает. Формат: обязан содержать дефис.

Разделение по форме кода позволяет проверке `pnpm check:literals` отличить допустимый литерал от нарушения.

### 5.2. Признаки элементов

`attribute_schema` справочника описывает допустимые признаки; `attributes` элемента хранит их значения. **Ветвление логики допустимо только по признакам.**

Перечень признаков, читаемых программой, объявлен в `packages/contracts/catalog-attributes.ts` и является кодом. Начальное наполнение `attribute_schema` формируется из этого перечня миграцией. Проверка: каждый признак, читаемый в коде, объявлен в перечне; каждый объявленный признак присутствует в схеме соответствующего справочника.

### 5.3. Начальный состав справочников

`is_provisional = true` означает «значение придумано нами, нормативного подтверждения нет» (Д-01). Этот признак виден на экране администрирования справочников отдельной пометкой, чтобы при внедрении было понятно, что подлежит замене в первую очередь.

|---|---|---|---|

### 5.4. Правила работы со справочниками

1. Удаление элемента, на который есть ссылки, запрещено ограничением `on delete restrict`. Вместо удаления — `is_active = false`.
2. Неактивный элемент не предлагается в новых формах, но отображается в существующих записях и в отчётах за прошлые периоды.
3. Изменение кода элемента разрешено: программа от него не зависит.
4. `valid_from` и `valid_to` ограничивают предложение элемента в форме по дате события, а не по текущей дате.

## 6. Расширяемая часть карточки события

Ядро карточки — типизированные столбцы (§ 9.1). Дополнительные поля — данные.

```sql
incident.extra_field (
  id            uuid primary key,
  kind_item_id  uuid null references ref.catalog_item(id),  -- null = поле для всех видов
  key           text not null,          -- латиница, snake_case
  label         text not null,          -- наименование в форме, по-русски
  data_type     incident.field_type_enum not null,  -- text|multiline|integer|number|boolean|date|catalog
  catalog_id    uuid null references ref.catalog(id),
  unit          text null,
  is_required   boolean not null default false,
  is_indexed    boolean not null default false,
  sort_order    integer not null default 0,
  min_value     numeric null,
  max_value     numeric null,
  max_length    integer null,
  ...обязательные колонки,
  unique (kind_item_id, key),
  unique (key) where kind_item_id is null
);
```

**Почему два ограничения, а не одно.** В PostgreSQL значения `NULL` в уникальном ограничении считаются различными, поэтому `unique (kind_item_id, key)` **не запрещает** завести два общих поля с одним ключом — то есть ровно то, ради чего написано. Второе, частичное ограничение закрывает случай общих полей.

**Дополнительно — триггер.** Ключ не может одновременно принадлежать общему полю и полю вида: попытка завести поле вида с ключом, уже занятым общим полем, и наоборот, отклоняется с текстом «Дополнительное поле с ключом «<ключ>» уже существует для всех видов событий. Выберите другой ключ.» Без этого триггера два поля с одним ключом складывались бы в одну ячейку `extra`, затирая друг друга, и отбор по точному совпадению давал бы разные результаты на разных записях.

Значения хранятся в `incident.incident.extra` типа `jsonb`, индекс `GIN (extra jsonb_path_ops)`.

**Порядок вывода в форме:** сначала общие поля (`kind_item_id IS NULL`), затем поля вида, внутри каждой группы — по `sort_order`, затем по `label`.

**Явное ограничение, которое нельзя обойти.** Фильтрация по дополнительному полю поддерживает **только точное совпадение и проверку наличия**. Диапазоны, сравнения и сортировка доступны только для полей ядра. Причина: динамическое поле не может получить собственный индекс без изменения схемы, а изменение схемы администратором противоречит П-1. Если по показателю нужны диапазоны и сортировка — он должен стать полем ядра, что является изменением контракта.

## 8. Общие правила целостности

1. Каждый внешний ключ объявляет поведение при удалении явно. По умолчанию `ON DELETE RESTRICT`. `ON DELETE CASCADE` допустим **только внутри агрегата**.
2. Мягкое удаление (`deleted_at`) применяется **только** в двух местах: `files.node` (корзина) и `chat.message` (пометка «удалено»). Везде ещё — явное состояние жизненного цикла. Придумывать новые мягкие удаления запрещено.
3. Все счётчики людей, домов и техники: `CHECK (col IS NULL OR col >= 0)`.
4. `NULL` в счётчике означает **«данных нет»**, `0` означает **«ноль»**. Это различие обязательно к отображению: пустое значение выводится как `—`, ноль выводится как `0`. Смешивать их запрещено — на этом различии стоит вся статистика.
5. Геометрия: SRID 4326 обязателен ограничением; полигоны проверяются `ST_IsValid`.
6. `occurred_at <= now() + interval '1 hour'` — защита от опечатки в году.
7. `closed_at >= registered_at`, `ended_at >= started_at`, `valid_to >= valid_from` — ограничениями `CHECK`.
8. Ограничение длины текста задаётся схемой запроса (`packages/contracts`), а не типом в базе. Тип в базе — `text`.
9. **Абсолютный адрес системы не хранится ни в одном столбце** (принцип П-5). Ссылки на объекты хранятся относительными путями, начинающимися с `/`. Исключения перечислены в `packages/db/url-allowlist.ts` и проверяются командой `pnpm check:urls`.

**Правило поля `is_emergency`.** При создании события значение берётся из признака `isEmergency` выбранного вида; `emergency_set_at` при этом остаётся пустым. **Далее оно редактируется вручную** обладателем разрешения `incident.card.register`, потому что отнесение происшествия к чрезвычайной ситуации зависит не только от вида, но и от последствий: пожар может быть и происшествием, и ЧС.

**Ручное изменение требует основания. Без основания значение не сохраняется.** Отнесение к чрезвычайной ситуации в государственном органе — формальное решение, и в отчёте наверх нужно уметь объяснить, почему пожар посчитали чрезвычайной ситуацией. Одной записи в журнале «кто-то переключил признак» для этого недостаточно.

- При ручном изменении обязательно заполнено **либо** `emergency_basis` (текст не короче 10 знаков), **либо** `emergency_document_id` (ссылка на документ, доступна с этапа 3). Ограничение: `check (emergency_set_at is null or emergency_basis is not null or emergency_document_id is not null)`.
- Одновременно заполняются `emergency_set_by_person_id` и `emergency_set_at`.
- Сохранение без основания отклоняется с кодом `VALIDATION_FAILED` и текстом «Укажите основание отнесения события к чрезвычайной ситуации: оно попадёт в отчёт.» (и симметрично при снятии признака).
- Запись журнала содержит прежнее и новое значение **и текст основания**.
- Основание показывается в карточке рядом с признаком и доступно в шаблонах печатных форм подстановкой `${основаниеЧС}`.
- Смена вида события **не переписывает** значение, выставленное вручную (`emergency_set_at` не пуст), — иначе уточнение вида молча меняло бы статистику ЧС задним числом. Если значение не выставлялось вручную, смена вида обновляет его из признака нового вида.

Индексы: `occurred_at DESC`, `owner_org_unit_id`, `kind_item_id`, `status`, `is_emergency`, GiST по `geom`, GIN по `search_tsv`, GIN по `extra`, составной `(owner_org_unit_id, occurred_at DESC)` для реестра.

`incident.attachment (id, incident_id, blob_id, name, description, ...)` — вложения.

`incident.duty_shift (id, org_unit_id, started_at, ended_at, status open|closed, opened_by_person_id, closed_by_person_id, handover_note)`. Частичный уникальный индекс: не более одной открытой смены на подразделение.

`incident.daily_summary (id, org_unit_id, duty_date, status draft|approved, figures jsonb, note text, approved_at, approved_by_person_id)`. Уникально по `(org_unit_id, duty_date)`. `figures` — посчитанные показатели, зафиксированные на момент утверждения: сводка не должна меняться задним числом при уточнении событий.

### 9.2. `pdn` — сведения о пострадавших

Отдельная схема, отдельный режим доступа (`05-ДОСТУП.md` § Персональные данные).

```sql
pdn.affected_person (
  id, incident_id uuid not null references incident.incident,
  status_item_id  uuid not null references ref.catalog_item,   -- AFFECTED_STATUS

  -- идентифицирующие столбцы: недоступны основной роли базы данных
  last_name       text null collate public.coll_tj,
  first_name      text null collate public.coll_tj,
  middle_name     text null collate public.coll_tj,
  birth_date      date null,
  sex             pdn.sex_enum null,
  document_number text null,
  address         text null,
  health_note     text null,

  -- обезличенные столбцы: доступны всем, кто видит событие
  age_group               pdn.age_group_enum null,   -- вычисляется триггером, см. правило ниже
  sex_public              pdn.sex_enum null,         -- копия sex, поддерживается триггером
  health_category_item_id uuid null                  -- HEALTH_CATEGORY
);
```

`pdn.age_group_enum`: `0-6`, `7-17`, `18-59`, `60+`, `unknown`.  Более дробная шкала не хранится: минимизация состава данных (Д-03).

**Правило вычисления возрастной группы — задано полностью, выбирать нечего.**

- Опорная дата — **`occurred_at` события**, к которому привязана запись, а не текущая дата. Возраст на момент события — то, что имеет смысл в статистике; возраст на момент ввода не имеет смысла и при загрузке прошлогодних данных даёт заведомо ложные группы.
- Значение — число **полных лет** на опорную дату. Границы: `0-6` = 0…6, `7-17` = 7…17, `18-59` = 18…59, `60+` = 60 и более.
- При `birth_date IS NULL` — `unknown`.
- Триггер: `BEFORE INSERT OR UPDATE OF birth_date, incident_id ON pdn.affected_person`. Изменение даты рождения и перенос записи на другое событие вызывают пересчёт.
- **После обезличивания (§ 8.6 `05-ДОСТУП.md`) значение не пересчитывается никогда:** `birth_date` обнулён, пересчитывать не из чего, а обезличенный столбец обязан пережить обезличивание. Триггер это учитывает: при `birth_date IS NULL` и уже заполненном `age_group` значение сохраняется.

`pdn.access_grant (id, person_id, incident_id null, affected_person_id null, purpose text, basis text, granted_at, granted_until, granted_by_person_id)` — обращение к сведениям с указанием основания.

### 9.6. `audit` — журнал действий

```sql
audit.event (
  id              bigserial primary key,
  occurred_at     timestamptz not null default now(),
  person_id       uuid null,
  assignment_id   uuid null,
  delegation_id   uuid null,          -- если действие совершено в порядке замещения
  session_id      uuid null,
  ip              inet null,
  request_id      text null,
  action          text not null,      -- 'incident.card.update'
  entity_schema   text not null,
  entity_table    text not null,
  entity_id       uuid null,
  entity_label    text null,          -- регистрационный номер или наименование на момент действия
  before_data     jsonb null,
  after_data      jsonb null,
  extra           jsonb null,
  prev_hash       bytea null,
  hash            bytea not null
);
```

- Только вставка. Роль приложения не имеет прав `UPDATE` и `DELETE` (выдано на уровне базы).
- `hash = sha256(prev_hash || канонический JSON строки без hash)`. Вставка сериализуется `pg_advisory_xact_lock`.
- `entity_label` хранится копией, потому что объект может быть переименован, а журнал обязан читаться спустя годы.
- **Изъятие для схемы `pdn`.** Для сущностей схемы `pdn` в `before_data` и `after_data` записываются **только имена изменённых столбцов** (`{"changed": ["last_name"]}`), значения идентифицирующих столбцов не записываются никогда, а `entity_label` формируется обезличенно: `«Пострадавший №N по событию <рег.номер>»`. Значения обезличенных столбцов (`status_item_id`, `age_group`, `sex_public`, `health_category_item_id`) записываются как обычно. Перечень запрещённых столбцов — `packages/contracts/pdn-protected-columns.ts`. Полное правило и его цена — `05-ДОСТУП.md` § 8.7.
- Хранение — постоянное. Записи журнала не подпадают под сроки хранения документов.

Печатная форма утверждённой версии обязана содержать: наименование должности и фамилию утвердившего, дату и время утверждения, регистрационный номер, номер версии.

```sql
              status meet.meeting_status_enum, host_person_id, org_unit_id, is_private boolean)
meet.participant (id, meeting_id, person_id null, display_name text, role meet.role_enum,
                  joined_at, left_at)
meet.recording (id, meeting_id, started_at, ended_at, duration_sec integer, size_bytes bigint,
                blob_id null, storage_state meet.storage_enum,  -- on_server|exported|deleted
                exported_at, exported_to text, export_act_id null,
                deleted_at, deleted_by_person_id)
meet.export_act (id, act_number text unique, act_date date, media_label text,
                 recordings_count integer, created_by_person_id)
```

**Правило удаления записи.** Переход `on_server → deleted` запрещён триггером. Допустимы только `on_server → exported → deleted`. Попытка удалить невыгруженную запись даёт отказ с текстом «Запись не выгружена на внешний носитель. Удаление невозможно.»

Право просмотра записи: участники совещания по умолчанию; остальные — по разрешению `meet.recording.read_any`.

## 10. Жизненные циклы и допустимые переходы

Состояния и переходы — **код**, а не данные: каждому переходу соответствует ветвь программы и проверка прав. Переход, отсутствующий в таблице, невозможен; попытка даёт `CONFLICT`.

### 10.1. Событие (`incident.status_enum`)

| Из | В | Условие | Требуемое разрешение |
|---|---|---|---|
| `draft` (черновик) | `registered` (зарегистрировано) | Заполнены обязательные поля; присваивается номер и `registered_at` | `incident.card.register` |
| `draft` | `cancelled` (аннулировано) | Указана причина | `incident.card.cancel` |
| `registered` | `clarifying` (уточняется) | — | `incident.card.update` |
| `registered` | `closed` (закрыто) | Заполнены итоговые показатели | `incident.card.close` |
| `clarifying` | `closed` | Заполнены итоговые показатели | `incident.card.close` |
| `closed` | `clarifying` | Указана причина переоткрытия | `incident.card.reopen` |
| `registered`, `clarifying`, `closed` | `cancelled` | Указана причина | `incident.card.cancel` |

`cancelled` — конечное состояние. Изменение аннулированного события запрещено. Аннулированное событие исключается из всех показателей аналитики, но остаётся в реестре с явной пометкой.

Редактирование по состояниям: `draft` — автором и имеющими право в своей области; `registered` и `clarifying` — по праву `incident.card.update`; `closed` — запрещено до переоткрытия; `cancelled` — запрещено.

### 10.2. Дежурная смена

`open` → `closed`. Закрытие требует, чтобы ни одно событие смены не осталось в состоянии `draft`. Открыть вторую смену в подразделении при открытой первой невозможно.

### 10.3. Суточная сводка

`draft` → `approved`. После утверждения `figures` не пересчитываются: уточнение событий задним числом не меняет утверждённую сводку. Изменение утверждённой сводки невозможно; при необходимости создаётся новая с пометкой «уточнённая» (поле `note`).

### 10.4. Документ (`doc.doc_status_enum`)

| Из | В | Условие |
|---|---|---|
| `draft` | `on_approval` | Есть версия, выбран маршрут |
| `on_approval` | `approved` | Все шаги вида `approve` завершены согласием |
| `on_approval` | `rejected` | Любой шаг завершён отказом |
| `on_approval` | `draft` | Отзыв автором |
| `rejected` | `draft` | Правка автором |
| `approved` | `draft` | **Невозможно.** Правка порождает новую версию: документ переходит в `draft`, создаётся версия N+1, маршрут проходится заново. Утверждённая версия N остаётся неизменной навсегда |
| любое, кроме `approved` | `cancelled` | Указана причина |

### 10.5. Версия документа

`черновая` → `утверждённая`. Обратного перехода нет. Утверждённая версия неизменяема (триггер).

### 10.6. Жизненный цикл хранения (`doc.lifecycle_enum`)

| Из | В | Кто или что вызывает |
|---|---|---|
| `active` (действующий) | `to_destroy` (к уничтожению) | Задание обхода сроков: наступил `retention_due_at` **и** нет действующей правовой блокировки |
| `active` | `permanent` (постоянное хранение) | Правило хранения с признаком `isPermanent` |
| `to_destroy` | `active` | Наложена правовая блокировка либо срок продлён архивистом |
| `to_destroy` | `destroyed` (уничтожен) | **Только** после утверждения акта уничтожения уполномоченным лицом |
| `permanent` | — | Конечное состояние |

**Автоматическое удаление отсутствует.** Наступление срока переводит объект в состояние `to_destroy` и не более того. Физическое удаление содержимого выполняется только по утверждённому акту. Сам акт хранится постоянно и уничтожению не подлежит.

Правовая блокировка (`office.legal_hold`) перебивает любой срок: пока блокировка не снята, переход в `to_destroy` невозможен, а объект, уже находящийся в `to_destroy`, возвращается в `active`.

### 10.7. Регистрация в канцелярии

`reserved` → `active` (успешная регистрация) или `reserved` → `void` (аннулирование с указанием причины). Аннулированный номер остаётся видимой строкой журнала и не выдаётся повторно.

### 10.8. Задача (`task.status_enum`)

| Из | В | Кто |
|---|---|---|
| `new` (новая) | `in_progress` (в работе) | Исполнитель принял |
| `new`, `in_progress` | `in_progress` с другим исполнителем | Делегирование вниз по дереву подразделений |
| `in_progress` | `submitted` (сдана) | Исполнитель отправил результат |
| `submitted` | `returned` (возвращена) | Постановщик вернул с замечанием |
| `returned` | `in_progress` | Исполнитель продолжил |
| `submitted` | `done` (принята) | Постановщик принял |
| любое, кроме `done` | `cancelled` | Постановщик, с указанием причины |

Делегирование допустимо только вниз по дереву подразделений и только на назначение, существующее на момент делегирования. Ответственность остаётся на первоначальном исполнителе: он видит задачу до её приёмки.

### 10.9. Запись совещания

`on_server` → `exported` → `deleted`. Прямой переход `on_server → deleted` запрещён триггером.

### 10.10. Отчёт

`queued` → `running` → `done` или `failed`. При `failed` заполняется `error_text` и пользователь получает уведомление с причиной на русском языке.

## 11. Шаблоны печатных форм

Шаблон — файл `.xlsx` или `.docx`, загружаемый делопроизводителем. Вёрстка печатной формы в программе запрещена (Д-01, П-1).

### 11.1. Единая грамматика подстановок

Для обоих форматов используются одинаковые ограничители `${` и `}` (для Word ограничители переопределяются при настройке библиотеки, чтобы делопроизводителю не приходилось помнить две грамматики).

| Конструкция | Значение |
|---|---|
| `${имя}` | Подстановка значения |
| `${имя\|дата}` | Формат `дд.ММ.гггг` |
| `${имя\|датавремя}` | Формат `дд.ММ.гггг ЧЧ:мм` |
| `${имя\|число}` | Целое с разделителями разрядов |
| `${имя\|число:2}` | Дробное с двумя знаками |
| `${имя\|деньги}` | Сумма с разделителями и обозначением `смн` |
| `${#блок}` … `${/блок}` | Повторяемая область |
| `${элемент.поле}` | Поле элемента внутри повторяемой области |
| `${^блок}` … `${/блок}` | Область, выводимая, если блок пуст |
| `${адресСистемы}` | Адрес системы из настройки `BASE_URL` **в момент формирования отчёта** |
| `${основаниеЧС}` | Основание отнесения события к чрезвычайной ситуации (`incident.emergency_basis`) |

**Excel.** Повторяемая область задаётся строкой, у которой в первом столбце стоит `${#блок}`, и строкой с `${/блок}`. Служебные строки удаляются, промежуточные строки повторяются с сохранением оформления, объединений и формул.

**Word.** Конструкции размещаются в тексте, в таблицах повторяемая область задаётся строкой таблицы.

### 11.2. Правила

1. Отсутствие в данных поля, упомянутого в шаблоне, — не ошибка: подставляется `—`. Иначе смена бланка ломала бы отчёт.
2. Наличие в данных поля, не упомянутого в шаблоне, — не ошибка.
3. Ошибка синтаксиса шаблона обнаруживается **при загрузке**, а не при формировании отчёта: делопроизводитель получает сообщение с номером строки или абзаца.
4. PDF получается конверсией уже заполненного `.docx` или `.xlsx`. Отдельного шаблона PDF не существует.
5. Перечень доступных полей для каждого вида шаблона показывается на экране управления шаблонами: делопроизводитель должен видеть, что можно вставить.
6. **Записывать в шаблон адрес системы буквой запрещено.** Ссылка на систему вставляется только подстановкой `${адресСистемы}`, иначе шаблон перестанет работать после переезда на домен Комитета (принцип П-5). Загрузка шаблона, содержащего строку, начинающуюся с `http://` или `https://` и совпадающую с текущим или прежним именем системы, отклоняется с пояснением.

## 12. Миграции

- Каталог `packages/db/migrations`, файлы `NNNN_имя.sql`, номер сквозной, четыре цифры.
- Применение — только вперёд. Откатов нет: на одном сервере откат схемы опаснее исправления.
- Применённые версии — в `sys.migration`.
- Миграция, удаляющая или переименовывающая столбец с данными, требует записи о решении и утверждения Держателем контракта.
- Начальное наполнение — `packages/db/seed`, применяется отдельной командой, помечает придуманные элементы справочников `is_provisional = true`.
- Проверка `test:db` выполняет: применение всех миграций на пустой базе (норматив Н-15), применение миграций поверх предыдущего выпуска, проверку прав ролей, проверку триггеров заморозки и запрета удаления.

## 13. Права ролей базы данных

| Роль | Назначение | Ограничение |
|---|---|---|
| `coes_owner` | Владелец схем, применение миграций | Используется только при развёртывании и обновлении |
| `coes_app` | Основная роль приложения | **Нет** прав `SELECT` на идентифицирующие столбцы `pdn.affected_person`; **нет** прав `UPDATE` и `DELETE` на `audit.event` |
| `coes_pdn` | Работа со сведениями о пострадавших | Используется **только** модулем `pdn` |
| `coes_backup` | Резервное копирование | Только чтение |

Проверка `test:db` содержит два утверждения:

1. Обращение к столбцу `pdn.affected_person.last_name` от имени `coes_app` завершается ошибкой базы данных `permission denied for column`. Это не проверка в программе — это право в базе.
2. После изменения записи о пострадавшем последняя запись `audit.event` от имени `coes_app` даёт `after_data ? 'last_name'` = `false`, а `entity_label` не содержит внесённой фамилии (Н-04, `05-ДОСТУП.md` § 8.7). Без этой проверки защита схемы `pdn` обходится через журнал.
